# 第一周：

## 项目名称

校园失物招领系统

## 目标用户

在校学生、教职工、校园管理员

## 优先实现业务场景

丢失物品的学生发布失物信息，管理员审核信息后对外展示；捡到物品的师生发布招领信息，失主提交认领申请，完成物品匹配对接。

## 核心模型 1：LostItem（失物记录）

属性：id、物品名称、物品类型、丢失地点、丢失时间、描述、发布人 id、状态、图片 url

## 核心模型 2：FoundItem（拾获物品记录）

属性：id、物品名称、物品类型、捡拾地点、捡拾时间、描述、发布人 id、状态、图片 url

## 第四周：业务建模更新

### 1. 本周核心业务流程
学生发布失物启事流程：用户提交失物信息 -> Controller 接收请求 -> Service 校验业务规则 -> 校验通过后调用 Repository -> 数据持久化到 MySQL 数据库。

### 2. 业务实体及其关系
本周实现了 2 个核心实体：
- User（用户）：发布失物的主体。
- LostItem（失物帖子）：记录具体的失物信息。

实体关系：User 和 LostItem 是一对多（1:N）的关系。一个用户可以发布多条失物帖子，一条失物帖子只能属于一个用户（通过 LostItem 表中的 user_id 外键关联）。

### 3. Service 层的业务规则
规则：发布失物时，必须填写“物品特征”（feature）。
实现位置：在 LostItemServiceImpl 的 createLostItem 方法中。如果传入的 feature 为空或仅包含空格，直接抛出 IllegalArgumentException 异常，并返回 400 状态码，拒绝保存至数据库。
